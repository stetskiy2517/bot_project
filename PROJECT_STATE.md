## 1. Принятое направление продукта

Основной интерфейс проекта — собственное Web/PWA-приложение. Telegram сохраняется как дополнительный интерфейс на будущее и не должен определять архитектуру ядра.

Базовый поток:

`Web/PWA -> web_app.py -> core/web_transport.py -> modules/router.py -> Smart Planner / Google Calendar`

Telegram использует то же ядро через `bot.py -> modules/router.py`.

Цель — персональный AI-секретарь руководителя, где календарь является первым рабочим модулем, а голос, задачи, память и другие функции подключаются к общему роутеру, а не создают отдельные приложения.

### Категоризация событий
Категоризация восстановлена и снова участвует в создании события.

Дефолтные категории:
- `work` — Работа — Google colorId 3;
- `health` — Здоровье — colorId 6;
- `rest` — Отдых — colorId 10;
- `travel` — Поездки — colorId 7;
- `personal` — Личное — colorId 5;
- `other` — Другое — colorId 1.

Категория определяется по содержанию события. Пользователь может изменить цвет каждой категории в `Настройки -> Категории и цвета` или оставить схему по умолчанию.

Настройки цветов хранятся отдельно для каждого пользователя. При создании события выбранный цвет передаётся в Google Calendar как `colorId`.

Пользователь подтвердил, что категоризация после восстановления работает.

## 3. Авторизация и многопользовательская модель

Принято решение не создавать отдельные email/password аккаунты. Google является одновременно способом входа и авторизацией Google Calendar.

Стабильная внешняя идентичность — Google `sub`; email и name являются метаданными.

Каждый пользователь должен иметь изолированные:
- Google credentials/token;
- timezone и календарные настройки;
- категории/цвета;
- pending state;
- будущую память, задачи и данные других модулей.

Автотесты проверяют изоляцию настроек между пользователями, включая пользовательские цвета категорий.

## 5. Текущая структура, которую сохраняем

Ключевые рабочие точки:
- `web_app.py` — Web/PWA HTTP/API entrypoint;
- `web/` — PWA frontend;
- `bot.py` — Telegram transport, вторичный интерфейс;
- `core/web_transport.py` — адаптер web-запроса к общему роутеру;
- `core/db.py` — SQLite и пользовательские настройки/Google identity;
- `modules/router.py` — общий intent/router;
- `modules/calendar*.py` — календарная логика;
- `modules/calendar_categories.py` — пользовательская категоризация и цвета;
- `modules/auth.py` — Google OAuth;
- `integrations/` — внешние интеграции;
- `tests/` — unit/E2E tests.

В репозитории остаются legacy-файлы старой реализации (`app.py`, старые helpers и т.п.). Не считать их новой целевой архитектурой и не переносить из них код без необходимости.

## 6. Известный технический долг / риски

До production необходимо отдельно закрыть:

1. Проверить модель внутренних ID Google-пользователей на отсутствие коллизий с Telegram user_id. Предпочтительная схема для web identity — отдельное пространство ID (например отрицательные внутренние ID), если это ещё не реализовано окончательно.
2. OAuth `state` для web должен быть привязан к browser session и проверяться до token exchange; не использовать nullable Telegram-style oauth state как компромисс.
3. Проверить и ужесточить Flask session cookies для HTTPS production: HttpOnly, SameSite, Secure; `WEB_SESSION_SECRET` должен быть сильным production secret.
4. Убрать/мигрировать неиспользуемые legacy web email/password настройки и таблицы, если они ещё остались после перехода на Google-only auth.
5. Вынести путь SQLite в конфигурацию (`DB_PATH`) и обеспечить persistent volume при Docker deployment.
6. `_user_state` сейчас процессный/in-memory: pending actions потеряются после restart и не подходят для нескольких workers. Перенести состояние в устойчивое per-user storage перед масштабированием.
7. Google tokens сейчас требуют отдельного security review хранения; перед production предусмотреть защиту credentials at rest и исключить секреты из логов.
8. PWA: проверить service worker cache/versioning и полноценные install icons/iOS behavior.
9. Добавить rate limiting и базовую защиту публичных API endpoints перед интернет-развёртыванием.
10. Добавить пользовательские сценарии disconnect Google / logout / удаление аккаунта и данных.
11. Очистить legacy-код и `.DS_Store`/`__pycache__` из репозитория отдельным безопасным этапом, не смешивая это с функциональными изменениями.
12. PR/ветка накопили большой объём изменений; перед merge в `main` провести отдельный финальный review и привести PR в актуальное состояние.

## 7. Что НЕ считать завершённым

Пока не считать production-ready:
- публичное интернет-развёртывание;
- production security hardening;
- устойчивое хранение pending/dialog state;
- полноценную проверку нескольких реальных Google-аккаунтов A/B на отсутствие cross-access;
- голосовое управление всеми будущими модулями;
- AI Sales Memory, Knowledge Engine, Market Radar и Sales Operating System — это направления дальнейшего продукта, а не подтверждённо завершённые подсистемы текущего MVP.
