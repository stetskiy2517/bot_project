## Текущая архитектура и реализованные блоки

### Ядро и безопасность

В `core/` разделены хранилища и общая инфраструктура: БД, identity, feature access, web security, transport, command safety, push, notification policy, undo, attention, память, заметки, задачи, навигация и другие состояния.

Критичные механизмы уже присутствуют:

- защита от повторного выполнения команд;
- изоляция данных по пользователю;
- CSRF/request transport;
- OAuth/session logic;
- Web Push и политика повторных уведомлений;
- ограниченный undo для обратимых действий;
- экспорт/удаление пользовательских данных;
- безопасный fallback при недоступности AI.

### Календарь и планирование

Реализованы календарь, создание/изменение событий, повторения, поиск свободного времени, пользовательские настройки, категории, работа с локацией и связанные действия. Свободные окна перепроверяются перед созданием события.

### Напоминания

Есть хранение, повторения, категории, редактор, push-доставка, dispatcher, политика ограниченных повторных уведомлений и quiet hours.

### Задачи

В текущем `main` модуль задач уже существует: API, planner, recurrence, storage и web UI. Поэтому старые документы, где задачи помечены как отложенные/отсутствующие, больше не являются источником истины.

### Заметки и библиотека

Реализованы заметки, контекстное продолжение заметок, ссылки/инструменты заметок, библиотека и восстановление части действий через undo.

### AI и память

Есть отдельная AI-интеграция, assistant API, AI memory, prompt architecture, работа с файлами и fallback для запросов, которые не обработаны обычным роутером.

Недоступность AI не должна останавливать базовые модули приложения: это покрыто отдельным тестом web fallback.

### Почта

Есть Gmail/IMAP интеграции, чтение и обработка писем, действия, вложения, автоматический анализ и web UI. Интеграционные тесты покрывают значительную часть логики, но не заменяют ручную проверку реального почтового аккаунта перед широкой бетой.

### Навигация

Есть отдельные модули навигации, мониторинга, уведомлений, recurring logic, semantic rules и несколько провайдеров маршрутизации. Навигация связана с календарным контекстом и пользовательской геопозицией.

### Проактивный секретарь

В проекте есть proactive engine, feedback store, daily review/briefing и attention center. Утренние/вечерние сценарии и уведомления ограничиваются пользовательскими настройками и защитными правилами.

### Админка

Есть admin API, admin store, metrics и отдельный web-интерфейс. Это уже реализованный блок, а не только идея дорожной карты.

## Подтверждённые риски и пробелы перед публичной бетой

### 1. Safari и физический iPhone

Автоматический browser CI использует Chromium. Размер мобильного viewport проверяется, но это не проверка Safari/WebKit и не проверка реального iPhone. Для продукта, которым активно пользуются с телефона, это обязательный ручной/автоматизированный этап перед внешней бетой.

### 2. GigaChat вернул HTTP 429 при последнем production deploy

Основное приложение и health-check не упали, а AI fallback остаётся безопасным. Но фактическая доступность AI зависит от внешнего лимита/квоты. Нужно отдельно контролировать 429, показывать понятный статус и не считать AI доступным только потому, что приложение живо.

### 3. Production health-check слишком узкий

Текущий scheduled monitor примерно раз в 15 минут проверяет только `/api/health` и поле `status=ok`.

Он не подтверждает:

- какой SHA реально работает на сервере;
- доступность AI;
- доставку push;
- доступность почты;
- доступность календарного провайдера;
- работоспособность ключевых пользовательских сценариев.

Для личной разработки этого достаточно как базового ping. Для публичной беты — нет.

### 4. `main` не защищён правилами GitHub

На момент аудита ветка `main` имеет `protected: false`, обязательные status checks на уровне branch protection не настроены.

Автодеплой сам по себе корректно ждёт успешный workflow `tests`, но отсутствие защиты ветки оставляет возможность прямого изменения `main` вне обычного PR-процесса. Перед внешним запуском это нужно закрыть.

### 5. Живые внешние интеграции требуют отдельного smoke

CI хорошо покрывает код, но не доказывает работу всех реальных внешних систем одновременно. Перед внешней бетой отдельно проверить на тестовом пользователе:

- OAuth;
- реальный календарь;
- Gmail/IMAP;
- ASR на физическом телефоне;
- Web Push в фоне;
- маршрутизацию;
- AI;
- восстановление после временной недоступности каждого провайдера.

Для дальнейшей разработки источником истины считать актуальный `main`, а не PR и snapshot от 12–14 сентября.

Текущая проверенная точка аудита: `39aa39b337a376698aca1cc16f6071328a3e0884`.

Следующие изменения должны сохранять принцип:

**запрос → намерение → параметры → проверка → выполнение → результат**,

а необязательные внешние сервисы не должны останавливать календарь, напоминания, заметки и другие базовые функции.

До привлечения внешних пользователей закрыть в таком порядке:

1. защита `main` и обязательные CI checks;

3. контроль AI 429/квоты и понятный degradation status;
4. расширенный production health с версией/SHA и несколькими безопасными synthetic checks;
5. ручной smoke реальных OAuth, calendar, mail, push, ASR и navigation интеграций;
6. после этого — публичная beta/домен/аналитика/тарифы и дальнейшая продуктовая разработка.
